# SentinelAI Backend Master Context

## Part 1 — System Philosophy, Architecture & Core Design

---

# Purpose

This document is the master architectural context for the SentinelAI backend.

It is intended to be consumed by AI coding agents and developers before implementation.

This document is **the source of truth** for every backend design decision.

Whenever an implementation decision conflicts with this document, this document always wins.

The objective is consistency rather than flexibility.

---

# What is SentinelAI?

SentinelAI is an **Enterprise AI Governance Platform**.

Its purpose is **not** to execute business logic.

Its purpose is **not** to become another API Gateway.

Its purpose is to become the **Governance Execution Layer** between autonomous AI agents and enterprise systems.

Every AI agent must pass through SentinelAI before reaching an enterprise API.

SentinelAI decides whether an AI action is allowed.

Only after governance approval can enterprise execution happen.

---

# Core Vision

Traditional enterprise systems assume:

User
↓

Backend
↓

Database

Modern AI systems are different.

AI Agents make autonomous decisions.

Agents choose tools.

Agents invoke APIs.

Agents spend money.

Agents modify enterprise data.

Agents therefore require governance before execution.

SentinelAI exists to become this governance platform.

# Why LangGraph?

Governance is naturally a graph.

Some requests terminate immediately.

Some require approvals.

Some skip nodes.

Some pause.

Some resume later.

Traditional REST orchestration becomes extremely difficult.

LangGraph naturally supports:

• Conditional routing

• Pause/resume

• State

• Branching

• Explainability

• Deterministic execution

Therefore LangGraph becomes the governance engine.

---

# Backend Architecture

SentinelAI follows a Hybrid Architecture.

```
                    FastAPI

             REST / WebSocket APIs

                     │

             LangGraph Runtime

                     │

             Governance Nodes

                     │

            Backend Domain Services

                     │

             Repository Layer

                     │

              PostgreSQL Database

                     │

        Enterprise API Adapter Layer

                     │

            External Enterprise APIs
```

Each layer has exactly one responsibility.

---

# Responsibilities of FastAPI

FastAPI is NOT responsible for governance.

FastAPI only:

• receives requests

• validates payload

• authentication of platform users

• websocket connections

• health endpoints

• invokes LangGraph

• returns responses

Business decisions never belong inside FastAPI routes.

---

# Responsibilities of LangGraph

LangGraph is responsible for orchestration.

It owns:

workflow

routing

pause

resume

shared state

conditional execution

node ordering

LangGraph never contains business logic.

Nodes invoke backend services.

---

# Responsibilities of Services

Every governance node should be extremely thin.

Example

```
Policy Node

↓

PolicyService

↓

PolicyRepository
```

Business logic lives inside services.

Never inside nodes.

Never inside controllers.

Never inside repositories.

---

# Responsibilities of Repository Layer

Repositories only communicate with databases.

Repositories never:

calculate risk

validate policies

execute approvals

check budgets

perform governance

Repositories perform CRUD.

Nothing else.

---

# Enterprise Adapter Layer

SentinelAI never calls enterprise APIs directly.

Every enterprise system gets its own adapter.

Example

```
SAPAdapter

StripeAdapter

RefundAdapter

BookingAdapter

MerchantAdapter

HRAdapter
```

Adapters isolate external APIs.

This prevents vendor lock-in.

---

# Why Adapters?

Without adapters:

Execution Node

↓

calls Stripe

↓

later Stripe changes API

↓

Execution Node changes

Bad architecture.

With adapters:

Execution Node

↓

PaymentAdapter

↓

Stripe

↓

later

↓

PaymentAdapter changes

Execution Node remains unchanged.

# Design Principles

The backend follows these principles.

## Single Responsibility

Every module has one responsibility.

## Stateless Services

Services should avoid shared mutable state.

## Deterministic Decisions

Governance must produce identical outputs for identical inputs.

No randomness.

## Explainability

Every governance decision must be explainable.

Every denial requires reasons.

Every approval requires reasoning.

## Auditability

Nothing should disappear.

Every governance request becomes immutable audit history.

## Separation of Concerns

Identity

≠

Policy

≠

Risk

≠

Budget

≠

Compliance

Each is independent.

# Agent Model

SentinelAI does not authenticate human users.

It governs autonomous AI agents.

Therefore agents receive a managed identity.

This identity is called:

**Agent Passport**

---

# Agent Passport

Every registered agent owns:

Passport ID

Agent Name

Owner

Department

Version

Status

Allowed APIs

Allowed Services

Trust Score

Risk Tier

Budget Profile

Policy Groups

Created Date

Last Activity

Reputation

This is NOT JWT.

This is NOT OAuth.

This is an enterprise-managed identity.

---

# Why Not JWT?

JWT authenticates users.

SentinelAI governs autonomous software agents.

Agent identity must be persistent.

Centralized.

Governed.

Auditable.

Therefore Agent Passport is the preferred identity model.

---

# Governance API

Agents never call enterprise APIs.

Instead they call:

```
POST

/governance/execute
```

The execution request represents intent.

Not execution.

Example

```
Agent

↓

"I want to refund ₹500."

↓

SentinelAI

↓

Decision

↓

Execute

↓

Return Response
```

The enterprise API becomes implementation detail.

---

# Governance Request Model

Every request contains two major sections.

Metadata

Execution

Metadata identifies the agent.

Execution describes the requested action.

Example

```
metadata

passportId

agentVersion

execution

service

operation

parameters
```

The governance system should not require agents to know enterprise endpoint URLs.

They express intent only.

---

# Governance Response

Responses are also standardized.

```
metadata

requestId

traceId

timestamp

governance

decision

risk

reasons

approvalStatus

result
```

This separates governance from execution.

---

# Governance Decisions

Every node communicates using standardized decisions.

Never invent custom statuses.

Supported decisions:

ALLOW

DENY

REQUIRE_APPROVAL

ESCALATE

ERROR

These decisions drive graph routing.

Every node speaks the same language.

# Governance Execution Philosophy

The graph should resemble a security checkpoint.

Identity

↓

Policy

↓

Firewall

↓

Risk

↓

Budget

↓

Compliance

↓

Approval

↓

Execution

Not every request reaches execution.

Most governance happens before execution.

Execution is intentionally the last meaningful operation.

---

# Important Rule

There must be exactly **one** location in the entire backend capable of invoking enterprise APIs:

**Enterprise Execution Node**

No service.

No controller.

No repository.

No utility.

No graph node.

No websocket handler.

No scheduler.

No helper.

No module is allowed to call enterprise APIs except through the Enterprise Execution Node and its adapters.

This invariant must never be violated.
