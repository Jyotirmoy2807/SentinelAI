# SentinelAI Frontend Master Context

## Part 1 — Frontend Philosophy, Architecture, UI Principles & Application Structure

---

# Purpose

This document defines the complete frontend architecture of SentinelAI.

It serves as the master implementation guide for frontend developers and AI coding agents.

The frontend is **not** just an interface.

It is the visualization layer of the Governance Platform.

Its responsibility is to make enterprise AI governance understandable, controllable and explainable.

---

# Frontend Vision

The frontend should answer four questions for an enterprise administrator.

1. Which AI Agents exist?

2. What are they allowed to do?

3. What are they doing right now?

4. Why was a decision made?

Everything in the UI should support answering one or more of these questions.

---

# Frontend Philosophy

SentinelAI is an Enterprise Governance Console.

It is **not** an ERP.

It is **not** a CRM.

It is **not** an Admin Dashboard template.

It is a Governance Platform.

Every page should reinforce that identity.

---

# Core Design Principles

The UI should feel like

Enterprise

Professional

Minimal

Fast

Explainable

Predictable

Modern

Avoid unnecessary animations.

Use motion only to explain execution.

---

# User Personas

The frontend primarily serves administrators.

Primary users include

Enterprise Administrator

Security Administrator

Compliance Officer

Platform Administrator

Operations Engineer

AI Governance Team

Developers are secondary users.

AI Agents never interact with this UI.

Examples

Agent

Policy

Approval

Governance Request

Enterprise API

Risk

Compliance

Type safety significantly reduces frontend defects.

The frontend should be feature-oriented.

Never organize by file type alone.

Recommended structure

```text

app/

modules/

components/

layouts/

pages/

hooks/

services/

store/

types/

utils/

assets/

styles/
```

```text
modules/

dashboard/

agents/

governance/

enterprise/

execution/

approvals/

audit/

settings/
```

Each module contains its own

Components

Hooks

Services

Types

Pages

# Navigation Philosophy

Navigation should mirror backend domains.

Never mirror backend endpoints.

Good

Agents

Policies

Approvals

Audit

Dashboard

Bad

Services

Repositories

ExecutionService

Nodes

Users should navigate by business concepts.

# Sidebar Structure

The permanent sidebar should contain

Dashboard

Agent Management

Governance Management

Enterprise API Registry

Live Governance

Human Approval

Audit & Explainability

Settings

Simulation Lab

# Top Navigation

The top navigation contains

Search

Notifications

Environment

User Profile

# UI Philosophy

Every page should answer

What am I looking at?

What actions are available?

What is the current status?

Approval Required

↓

# Drawers

Examples

Agent Details

Audit Details

Execution Details

---

# Notifications

Notifications communicate

Success

Failure

Warning

Information

They should never explain governance.

---

# Loading States

Never leave blank pages.

Every request should have

Skeletons

Loading indicators

Progress states

This improves perceived performance.

---

# Empty States

Every module should have meaningful empty states.

Example

"No Agents Registered"

↓

Button

Register Agent

Never display empty tables without guidance.

---

# Error States

Every page should handle

Network Failure

Permission Denied

Unexpected Error

Retry

Errors should explain next steps.

---

# Frontend State Management

State is divided into three categories.

Server State

Managed using React Query.

Examples

Agents

Policies

Audit

Approvals

Enterprise APIs

---

UI State

Managed using Zustand.

Examples

Sidebar

Theme

Selected Agent

Filters

Current Tab

Open Drawers

---

Local State

Managed using React hooks.

Examples

Input Fields

Form Values

Modal Visibility

Temporary Selection

Never place local component state inside the global store.

```text

↓

API Service

↓

Axios Client

↓

FastAPI
```

Components should never make HTTP requests directly.
